ECS & Scene

Cách engine tổ chức dữ liệu: Entity/Component/Scene, hệ thống Reflection (đọc/ghi field một cách generic), và vòng đời Play/Stop.

Entity, Component, Scene

Engine dùng EnTT làm ECS lõi (registry sparse-set, không tự viết ECS riêng). Duality::Entity là handle mỏng bọc quanh entt::entity + con trỏ Scene* sở hữu nó: 

class Entity {
public:
    template<typename T, typename... Args> T& AddComponent(Args&&... args);
    template<typename T> T& GetComponent();
    template<typename T> bool HasComponent() const;
    template<typename T> void RemoveComponent();

    entt::entity Handle() const;
    Scene* GetScene() const;
    operator bool() const; // false nếu là entity rỗng/mặc định -- quy ước "falsy" dùng khắp engine
};

Mọi entity được tạo qua Scene::CreateEntity luôn có 4 component bắt buộc, tự động thêm sẵn: TransformComponent, NameComponent, TagComponent, HierarchyComponent (quản lý parent/children), và ActiveComponent. File scene cũ thiếu key nào trong số này khi load vẫn tự nhận giá trị mặc định — không cần code migrate.

Component là gì trong engine này?

Một struct C++ thuần (POD-ish), không hành vi (matching quy ước ECS chuẩn: dữ liệu và logic tách rời — logic nằm ở các hệ thống như SceneRenderer, Scene::OnRuntimeUpdate, không phải trong component). Ví dụ: 

struct SpriteRendererComponent {
    glm::vec2 Size{ 32.0f, 32.0f };
    glm::vec4 Color{ 1.0f, 1.0f, 1.0f, 1.0f };
    AssetRef Texture; // tham chiếu asset qua GUID -- xem trang Asset Pipeline
};

Reflection: TypeRegistry + FieldHandle

Thay vì hand-code UI Properties panel và serialize riêng cho từng loại component (dễ quên đồng bộ), engine dùng một hệ reflection tự viết (không phải entt::meta, một lựa chọn đơn giản hoá có chủ đích): mỗi component đăng ký một lần với TypeRegistry::Register<T>, liệt kê field qua MakeField: 

// Reflection.cpp -- đăng ký một lần lúc khởi động
TypeRegistry::Register<SpriteRendererComponent>("Sprite Renderer", false, {
    MakeField("Size", &SpriteRendererComponent::Size),
    MakeColorField("Color", &SpriteRendererComponent::Color), // đánh dấu "đây là màu", không phải vec4 thường
    MakeField("Texture", &SpriteRendererComponent::Texture),
});

MakeField dùng pointer-to-member, tạo ra một FieldHandle type-erased (Get(void*) -> FieldValue, Set(void*, FieldValue)). Từ một lần đăng ký đó, engine tự động có:

  • Properties panel — vẽ đúng widget theo kiểu field (DragFloat, ColorEdit, Combo cho enum, drag-drop cho AssetRef...) mà không cần code riêng cho từng component.
  • SceneSerializer — lưu/đọc JSON generic qua FieldValueToJson/JsonToFieldValue.
  • + Add Component — liệt kê mọi type đã đăng ký chưa có trên entity đang chọn.

FieldValue là một std::variant gồm mọi kiểu field engine hỗ trợ: int, float, bool, std::string, glm::vec2/vec3/vec4, Color4, AssetRef, EntityRef, và các enum riêng của engine (Screen, ProjectionType, BodyType...).

Vì sao không dùng entt::meta? Quyết định thiết kế có chủ đích từ đầu dự án — một hệ reflection tự viết đơn giản, dễ đọc, đủ dùng cho quy mô editor này, thay vì phụ thuộc một hệ reflection tổng quát nặng hơn nhiều so với nhu cầu thực tế.

DUALITY_PROPERTIES — reflection cho script

BehaviourComponent chỉ biết tên class (chuỗi), không có field riêng để đăng ký với TypeRegistry theo cách trên (không gắn với một Entity theo kiểu "component" thông thường). Field public của một Behaviour hiện lên Properties panel qua macro riêng: 

class BounceBehaviour : public Duality::Behaviour {
public:
    float Amplitude = 40.0f;
    float Speed = 8.0f;
    Duality::EntityRef Target;

    DUALITY_PROPERTIES(BounceBehaviour, Amplitude, Speed, Target)
};

Một dòng macro duy nhất liệt kê tên field đã khai báo, sinh ra static std::vector<FieldHandle> Fields() qua một FOR_EACH macro biến thiên (portable, không cần code-generation ngoài) — hoàn toàn tuỳ chọn, script không có dòng này thì đơn giản là không có field nào hiện ở Inspector.

Vì sao không phải DUALITY_PROPERTY() float speed; trên từng field? Không khả thi trong C++ thuần không có bước code-generation quét header — một macro gắn trên một field không có cách nào tự biết tên/kiểu của chính nó hay với tới danh sách field của cả class. DUALITY_PROPERTIES (lấy ý tưởng từ thư viện ImReflect trong hệ sinh thái ImGui) đạt cùng mục tiêu "không cần viết tay MakeField()" bằng một dòng ở cấp class.

Vòng đời Play/Stop

Scene::OnRuntimeStart() tạo body Box2D/Bullet cho mọi Rigidbody, và khởi tạo (OnCreate()) mọi Behaviour. Scene::OnRuntimeUpdate(deltaTime) chạy mỗi frame: step physics, xử lý sự kiện collision/trigger, gọi OnUpdate cho mọi Behaviour đang active. Scene::OnRuntimeStop() dọn dẹp — gọi OnDisable/OnDestroy cuối, giải phóng physics world.

Trong Editor, bấm Play chụp một snapshot JSON trong bộ nhớ (SceneSerializer::SerializeToJson) ngay trước OnRuntimeStart; Stop gọi OnRuntimeStop rồi Scene::Clear() + DeserializeFromJson(snapshot) để phục hồi chính xác trạng thái trước Play — mọi thay đổi Transform do script, kết quả vật lý, entity Instantiate/destroy lúc Play đều bị hoàn tác, giống hệt Unity.

Screen: "hai thế giới" Top/Bottom

3DS có hai màn hình vật lý (Top 400×240 không chạm, Bottom 320×240 có chạm) — đây là khái niệm hạng nhất trong engine, không phải chi tiết implementation: enum class Screen { Top, Bottom } xuất hiện trên CameraComponent::Screen, UIRectComponent::Screen, và xuyên suốt API script (FindEntityInTopScreen, ScreenPointToRay3D...). ScreenGroupComponent (tag, gắn vào entity gốc) phân loại cả subtree thuộc về màn nào; entity không gắn tag ("Ungrouped") vẫn hiện theo vị trí tương đối camera.
